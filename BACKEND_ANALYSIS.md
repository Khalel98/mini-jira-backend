# Анализ бэкенда проекта `node-trainee`

> Документ создан для обучения — подробный разбор архитектуры, технологий, потока данных, безопасности и потенциальных проблем в текущей реализации.

## 1. Общий стек технологий

| Категория | Технология | Версия |
|---|---|---|
| Runtime | Node.js | — |
| Веб-фреймворк | Express | `^5.2.1` |
| База данных | PostgreSQL | `postgres:18` (Docker) |
| Драйвер БД | `pg` (raw SQL, без ORM) | `^8.23.0` |
| Валидация | Zod | `^4.4.3` |
| Аутентификация | JWT (`jsonwebtoken`) | `^9.0.3` |
| Хэширование паролей | `bcrypt` | `^6.0.0` |
| CORS | `cors` | — |
| Конфигурация | `dotenv` | — |

Важно: **ORM не используется** — все SQL-запросы написаны руками с параметризацией (`$1, $2, ...`), что защищает от SQL-инъекций, но требует дисциплины разработчика.

Тестового фреймворка нет — `npm test` — заглушка. `npm run migrate` / `npm run seed` тоже не настроены как скрипты — файлы `src/db/migrate.js` и `src/db/seed.js` запускаются напрямую через `node`.

## 2. Инфраструктура (`docker-compose.yml`, `.env`)

```yaml
postgres:18
POSTGRES_USER=postgres
POSTGRES_PASSWORD=postgres   # дефолтный dev-пароль
POSTGRES_DB=node_trainee
ports: 5434:5432
volume: postgres_data -> /var/lib/postgresql
```

`.env` содержит:
- `PORT` — порт приложения (см. проблему ниже — не используется!)
- `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` — доступ к Postgres
- `JWT_SECRET` — секрет для подписи токенов (слабый dev-пример, в проде должен быть длинной случайной строкой)

## 3. Точка входа — `src/server.js`

Здесь собирается всё приложение:
1. `express()` + `cors()` (открытый CORS — разрешены все origin) + `express.json()`.
2. Роут `GET /profile` объявлен прямо тут (не в контроллере) — просто отдаёт `req.user` из middleware.
3. Подключаются роуты: `/auth`, `/users`, `/projects`, `/projects/:id/members`, `/projects/:id/columns`, `/columns`, `/tasks`.
4. В конце регистрируется `errorHandler` — глобальный обработчик ошибок Express (4 аргумента).
5. Асинхронно (без `await`) проверяется соединение с БД (`SELECT NOW()`) и запускаются миграции — **но `app.listen` вызывается не дожидаясь этого**.

### ⚠️ Проблемы в этом файле
- `app.listen(3000, ...)` — **порт хардкоднут**, хотя `.env` содержит `PORT` и `dotenv` загружен. Если поменять `PORT` в `.env`, ничего не изменится.
- Миграции запускаются "в фоне" без ожидания — сервер может начать принимать запросы до того, как схема БД готова (race condition).
- Нет обработчика 404 для несуществующих маршрутов (используется дефолтный Express-ответ, не JSON).

## 4. Слой базы данных

### `src/db.js`
Создаёт единственный (singleton) `pg.Pool` из переменных окружения. Нет `pool.on('error', ...)` — если "протухший" клиент в пуле выкинет ошибку, это может привести к неотловленному исключению и падению процесса. Нет настройки `ssl`/`max`.

### `src/db/migrate.js`
Это не классическая система миграций (нет таблицы версий, нет knex/umzug) — это **самописный идемпотентный скрипт**, который запускается при каждом старте сервера и при каждом запуске seed-скрипта. Логика:

1. Добавляет колонку `role` в `users` (`DEFAULT 'member'`), если её нет.
2. Если админов 0 — назначает админом самого раннего пользователя (`ORDER BY id LIMIT 1`) — механизм "бутстрапа" первого админа.
3. Создаёт таблицу `project_members` (составной PK `project_id, user_id`, FK с `CASCADE`).
4. Создаёт таблицу `task_columns` (колонки Kanban-доски).
5. Добавляет в `tasks` колонки `column_id`, `assignee_id`, `position`, `type`, `priority`.
6. Бэкфиллит `project_members` — владельцы проектов автоматически становятся их участниками.
7. Создаёт дефолтные колонки `To Do / In Progress / Done` для проектов, у которых их ещё нет.
8. Если есть старая колонка `status` в `tasks` — мигрирует значения `todo/in_progress/done` в новые `column_id`.
9. Любые "осиротевшие" задачи без `column_id` привязываются к первой колонке проекта.
10. `ALTER COLUMN column_id SET NOT NULL`.
11. Удаляет старую колонку `status`, если она была.

**Важный момент для обучения**: в коде нет `CREATE TABLE users/projects/tasks` — миграция предполагает, что эти три базовые таблицы уже существуют. Значит, поднять проект "с нуля" одним `docker-compose up` + `node src/db/migrate.js` **не получится** — не хватает начальной схемы. Это типичная ситуация в реальных проектах, когда часть истории миграций "потерялась", и хороший повод для учебного упражнения: написать недостающий `CREATE TABLE IF NOT EXISTS`.

### `src/db/seed.js`
Скрипт для наполнения БД тестовыми данными:
- Сначала вызывает `runMigrations()`.
- **`TRUNCATE TABLE tasks, task_columns, project_members, projects, users RESTART IDENTITY CASCADE`** — безусловно стирает данные в 5 таблицах и сбрасывает автоинкременты. Нет проверки `NODE_ENV !== 'production'` — если случайно запустить этот файл против продовой БД, будут удалены все данные.
- Хэширует bcrypt-ом (cost=10) два пароля: `"password123"` и `"admin123"` (это то, что вы видели выделенным в редакторе — [seed.js:104](src/db/seed.js#L104)). Это учебные/dev-данные, в реальном проекте такие пароли не должны попадать даже в seed-скрипты как "правдоподобные" — лучше генерировать случайные и печатать в консоль при первом запуске.
- Создаёт 1 админа + 3 обычных пользователя, 2 демо-проекта с участниками, колонками и задачами.
- В конце — `process.exit(0)` / `process.exit(1)`.

## 5. Middleware

### `asyncHandler.js`
Классический паттерн-обёртка для async-роутов Express:
```js
const asyncHandler = (fn) => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);
```
Гарантирует, что любая ошибка/reject внутри async-контроллера попадёт в `next(error)`, а не "потеряется" (без этого Express до версии 5 не ловит rejected промисы автоматически — в Express 5 это уже частично исправлено, но явная обёртка всё равно хорошая практика).

### `authMiddleware.js`
- Читает заголовок `Authorization`, ожидает формат `Bearer <token>`.
- Берёт токен как `header.split(" ")[1]` — **не проверяет, что первое слово именно `"Bearer"`** — заголовок `"Foo <token>"` тоже сработает. Мелкий, но показательный баг для разбора на занятии.
- `jwt.verify(token, JWT_SECRET)` → при успехе `req.user = decoded` (payload: `userId, email, role, iat, exp`).
- Любая ошибка верификации (истёк, невалиден, неверный секрет) → 401 "Invalid or expired token" (без утечки деталей — это хорошо).

### `requireAdmin.js`
`req.user?.role !== "admin"` → 403. Просто проверяет роль, зашитую в JWT.

**Важная проблема для разбора**: роль пользователя "заморожена" в токене на момент логина (срок жизни токена — 1 час). Если админа разжаловали в обычного пользователя в БД — его старый токен всё ещё будет работать как админский до истечения. И наоборот — свежепромоутнутый админ должен перелогиниться, чтобы получить новый токен с ролью `admin`.

### `errorHandler.js`
Логирует ошибку в консоль и **всегда** отвечает 500 "Internal server error" — не различает типы ошибок (это нормально, так как ожидаемые ошибки — 400/401/403/404/409 — контроллеры обрабатывают сами и отправляют ответ до того, как долетит до этого хендлера).

## 6. Авторизационная модель (`src/utils/projectAccess.js`)

Два хелпера, оба с параметризованными запросами (без риска SQL-инъекций):
- `getAccessibleProject(projectId, userId)` — проверка **членства** в проекте (JOIN `projects` + `project_members`).
- `getOwnedProject(projectId, userId)` — проверка **владения** проектом (`WHERE user_id = $2`).

В приложении фактически используются **три уровня доступа**:
1. **Глобальный админ** (`requireAdmin`) — управление пользователями, создание/удаление проектов.
2. **Владелец проекта** (`getOwnedProject`) — управление участниками, переименование/удаление проекта.
3. **Участник проекта** (`getAccessibleProject`) — создание/изменение/удаление колонок и задач.

Это разумная модель, но она **нигде не документирована** и местами противоречива (см. раздел 8) — хороший пример того, что в реальных проектах авторизационная логика должна быть явно описана и покрыта тестами.

## 7. Контроллеры и бизнес-логика

### `auth.controller.js`
- `register`: валидация через Zod → `bcrypt.hash(password, 10)` → **первый зарегистрированный пользователь автоматически становится админом** (`SELECT COUNT(*) FROM users`). При конфликте email (код Postgres `23505`) → 409.
  - *Учебный момент*: проверка count и последующий insert не в одной транзакции → теоретическая race condition при двух одновременных регистрациях, когда в БД 0 пользователей.
- `login`: ищет пользователя по email, сравнивает пароль через `bcrypt.compare`. При неудаче — **одинаковое** сообщение "Invalid email or password" независимо от того, что не так (email или пароль) — это правильная практика, защищающая от enumeration-атак. При успехе — `jwt.sign({userId, email, role}, JWT_SECRET, {expiresIn: "1h"})`.
  - *Отсутствует*: rate limiting / защита от брутфорса на логин (нет lockout, нет задержек, нет CAPTCHA).

### `project.controller.js`
- `createProject` — единственное место в проекте, где используется явная **транзакция** (`BEGIN/COMMIT/ROLLBACK` через `pool.connect()` + `client.release()` в `finally`): создаётся проект, владелец добавляется как участник, создаются дефолтные колонки. Хороший пример правильного паттерна для обучения.
- `updateProject`/`deleteProject` — требуют владения (route: `requireAdmin`, контроллер: `getOwnedProject`).

### `column.controller.js`
CRUD Kanban-колонок, доступ — по членству в проекте (не по владению). `deleteColumn` защищает от удаления последней колонки и колонки с задачами внутри — хорошая defensive-логика.

### `projectMember.controller.js`
- `addMember` — требует владения, использует `ON CONFLICT (project_id, user_id) DO NOTHING` + проверку количества вставленных строк для определения "уже участник" (409) — элегантный способ избежать race condition между "проверить существование" и "вставить".
- `removeMember` — явно запрещает удалять владельца проекта из участников.

### `task.controller.js`
Самая сложная логика — `moveTask` (drag-and-drop на Kanban-доске):
- Валидирует целевую колонку/позицию, проверяет доступ, что колонка принадлежит тому же проекту.
- В транзакции пересчитывает позиции всех задач в целевой колонке (вставляет перемещаемую задачу в нужное место массива), затем **обновляет позиции по одной строке в цикле** (N отдельных `UPDATE`) — рабочий, но неэффективный подход (O(n) запросов вместо одного batch-запроса `UPDATE ... FROM (VALUES ...)`). Хороший пример для урока по оптимизации SQL.
- Если задача переехала между колонками — также перенумеровывает оставшиеся задачи в исходной колонке.

### `user.controller.js`
`getUsers` — простой список для админов, но **не возвращает поле `role`**, хотя логично было бы его показывать.

## 8. Схемы валидации (Zod)

Общий паттерн: `createXSchema` + `updateXSchema = createXSchema.partial()`. Исключение — `task.schema.js`, где `updateTaskSchema` объявлен **отдельно**, а не через `.partial()` от `createTaskSchema` — риск разъехаться при будущих изменениях (дублирование логики).

- `user.schema.js`: пароль — минимум 6 символов, без требований к сложности (в реальном проекте — стоит усилить).
- `task.schema.js`: enum `type: ["task","bug","story"]`, `priority: ["low","medium","high"]`.

## 9. Полная карта API

| Метод | Путь | Требуемый доступ |
|---|---|---|
| GET | `/profile` | JWT |
| POST | `/auth/register` | публичный |
| POST | `/auth/login` | публичный |
| GET | `/users` | JWT + admin |
| GET | `/projects` | JWT (список своих проектов) |
| GET | `/projects/:id` | JWT + членство |
| POST | `/projects` | JWT + admin |
| PATCH `/projects/:id` | JWT + admin + владение |
| DELETE `/projects/:id` | JWT + admin + владение |
| GET `/projects/:id/members` | JWT + членство |
| POST `/projects/:id/members` | JWT + admin + владение |
| DELETE `/projects/:id/members/:userId` | JWT + admin + владение |
| GET/POST `/projects/:id/columns` | JWT + членство |
| PATCH/DELETE `/columns/:columnId` | JWT + членство |
| GET/POST `/tasks` | JWT + членство |
| GET/PATCH/DELETE `/tasks/:id` | JWT + членство |
| PATCH `/tasks/:id/move` | JWT + членство |

**Несостыковка модели доступа** (хороший кейс для обсуждения на занятии): роуты `/projects/:id/members` и изменение проекта требуют одновременно `requireAdmin` **и** владения проектом в контроллере. Если в системе появится второй админ (не владелец конкретного проекта), он пройдёт `requireAdmin`, но упрётся в `getOwnedProject` и получит **404 "Project not found"** — хотя проект существует, просто он не его владелец. Ошибка 404 здесь маскирует то, что по сути является 403 — с точки зрения UX и отладки это сбивает с толку.

## 10. Сводка находок для разбора на занятии

### Проблемы безопасности / надёжности
1. **`app.listen(3000, ...)`** игнорирует `process.env.PORT` — [server.js](src/server.js).
2. Сервер стартует, не дождавшись успешного подключения к БД/миграций — race condition при старте.
3. `authMiddleware` не проверяет, что схема токена именно `"Bearer"` — берёт `split(" ")[1]` без проверки первого элемента.
4. Роль в JWT "замораживается" на час — изменения роли в БД не подхватываются до перевыпуска токена.
5. Нет rate limiting на `/auth/login` — уязвимость к брутфорсу.
6. `seed.js` делает `TRUNCATE ... CASCADE` без проверки окружения — опасно при случайном запуске не туда.
7. Race condition при определении "первого админа" в `register` (не в транзакции).
8. `pool` без обработчика `error` — потенциальный неотловленный краш при обрыве соединения.
9. Слабый `JWT_SECRET` и пароли БД в `.env` — нормально для dev, недопустимо для прода.

### Архитектурные несоответствия
10. Три уровня авторизации (админ / владелец / участник) не задокументированы и местами конфликтуют (см. п. 9 карты API).
11. `updateTaskSchema` продублирован вместо `.partial()` от `createTaskSchema`.
12. В `migrate.js` отсутствует базовый `CREATE TABLE` для `users/projects/tasks` — проект нельзя развернуть "с нуля" только этим скриптом.

### Хорошие практики, которые стоит отметить
13. Все SQL-запросы параметризованы — нет SQL-инъекций.
14. `createProject` — образцовое использование транзакций (`BEGIN/COMMIT/ROLLBACK`, `client.release()` в `finally`).
15. `login` отдаёт одинаковую ошибку для неверного email/пароля — защита от enumeration.
16. Пароли никогда не возвращаются в ответах API.
17. `addMember` использует `ON CONFLICT DO NOTHING` + проверку affected rows вместо отдельного select-перед-insert — избегает race condition.
18. Идемпотентные миграции с `IF NOT EXISTS` — безопасно перезапускать.

## 11. Возможные учебные упражнения на основе этого проекта

1. Исправить `app.listen` — использовать `process.env.PORT`.
2. Дождаться `runMigrations()` перед `app.listen` (либо использовать паттерн graceful startup).
3. Добавить `CREATE TABLE IF NOT EXISTS` для базовых таблиц, чтобы проект поднимался с нуля.
4. Добавить rate-limiting middleware (например `express-rate-limit`) на `/auth/login`.
5. Переписать `moveTask`, чтобы обновлять позиции одним batch-запросом.
6. Добавить `pool.on('error', ...)`.
7. Разобрать и унифицировать модель доступа (admin/owner/member) — возможно, ввести middleware `requireOwnerOrAdmin`.
8. Написать тесты (например, на Jest/Vitest + supertest) для auth-флоу и task move-логики.
